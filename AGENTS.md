# AGENTS.md

Guidance for AI agents (and humans) working in the **planet-muluna** repository.

## What this project is

`planet-muluna` is a **Factorio 2.1 mod** that adds Muluna, a moon of Nauvis, plus a
large amount of cross-mod interoperability work. It is not a normal application:
there is no build step, no server, and no compiled artifact. The "code" is Lua that
Factorio loads at specific **load stages**, and the "output" is a zip that is
published to the Factorio mod portal by CI.

- Language: **Lua 5.2** (Factorio's embedded interpreter; editor config targets 5.2).
- Requires: Factorio **2.1+**, the **Space Age** expansion, and `PlanetsLib`.
- Author/maintainer: MeteorSwarm.
- Mod portal: https://mods.factorio.com/mod/planet-muluna
- Version is sourced from `info.json` (`"version"`), which is bumped automatically by CI.

There are **no automated tests you can run from a shell.** Verification means loading
the mod in Factorio and checking for crashes. See [Verifying changes](#verifying-changes).

## Repository layout

```
  planet/                 Muluna planet, asteroids, atmosphere, appearance
  overrides/              Mutations of vanilla (and other mods') prototypes
  final-fixes/            Deferred prototype patches that must run last
  mod-data/               Custom `mod-data` prototypes carrying constants between stages

```

## The Factorio load stages (most important concept)

Factorio runs a mod's Lua multiple times, in a fixed order, exposing different globals
each time. Code must be written to run at the correct stage(s).

1. **settings** — `settings.lua`, `settings-updates.lua`. `data` exists for settings only.
2. **data / data-updates / data-final-fixes** — prototype stage. `data.raw` is fully populated;
   `data:extend` is available. Load order: `data.lua` → `data-updates.lua` → `data-final-fixes.lua`,
   interleaved with other mods' same-named files.
3. **control** — `control.lua` and `scripts/*`. `game`, `script`, `storage`, `prototypes`,
   `rendering`, `remote` exist. `data` does **not** exist here.

`lib/get-stage.lua` classifies the stage:

```lua
if data and data.raw and not data.raw.item["iron-plate"] then return "settings"  -- early data
elseif data and data.raw then return "data"                                       -- any prototype stage
elseif script then return "control"
```

Note the limitation: **all three prototype files report `"data"` (the settings vs data
distinction only catches the earliest phase).** If code needs to distinguish
data-updates / data-final-fixes, it must be placed in the corresponding file rather than
branching on the stage.

`api.lua` runs in both prototype and control stages and sets `Muluna.stage`. The `api.lua`
file itself has two branches:

```lua
if Muluna.stage == "data" then
    -- require resource generation, icons, names, constants; register muluna-constants mod-data
elseif Muluna.stage == "control" then
    Muluna.constants = prototypes.mod_data["muluna-constants"].data
    Muluna.events = require("lib.events")
    ...
end
```

**Guard prototype-only code with `Muluna.stage == "data"` when a module might also be
loaded from control,** and never touch `data.raw` in control stage.

## The `Muluna` global API (`api.lua`)

Almost every file starts with `local rro = Muluna.rro`. Key members:

- `Muluna.stage` — `"settings"` / `"data"` / `"control"`.
- `Muluna.rro` — the **remove/replace object** library (`lib/remove-replace-object.lua`).
  This is the primary tool for editing prototype tables. Highlights:
  - `rro.remove(list, object)`, `rro.replace(list, old, new)`, `rro.replace_no_duplicates(...)`
  - `rro.soft_insert(list, object)` — insert only if not already present (used constantly for
    adding ingredients/prerequisites/effects without creating duplicates).
  - `rro.deep_equals(a, b)` — structural equality; the special string `"_any"` matches anything,
    and functions are treated as predicates. This is why patches can use `{"space-science-pack","_any"}`.
  - `rro.merge(old, new)` — deep-copies `old` then merges `new` (supports function values and `"_nil"`
    to delete a field). A custom replacement for `util.merge` (see commit history: `util.merge`
    caused cross-mod breakage).
  - `rro.find_many`, `rro.contains`, `rro.count`, `rro.keys`, `rro.range`, `rro.copy_fields`, ...
- `Muluna:extend(new_data)` — **preferred over `data:extend`**. It normalizes recipes
  (`hide_from_recipe_gui`) and tech research triggers, then calls `data:extend`.
- `Muluna.constants` — a table carried between stages via a `mod-data` prototype
  (`muluna-constants`, populated in `prototypes/mod-data/constants.lua`).
- Data-stage helpers: `Muluna.resource`, `Muluna.resource_autoplace`, `Muluna.icons`
  (`lib/dual-item-icon`), `Muluna.img` (`lib/images`), `Muluna.pipe_pictures`,
  `Muluna.telescopes`, `Muluna.machine_scaling`, etc.
- Control-stage helpers: `Muluna.events`, `Muluna.complete_research`.

## Event handling (control stage)

Do **not** call `script.on_event` directly. Use the forked multi-handler system in
`lib/events.lua`:

```lua
Muluna.events.on_event(defines.events.on_built_entity, my_handler)
Muluna.events.on_event(Muluna.events.events.on_built, my_handler) -- group of events
```

- `Muluna.events.events.on_built`, `.on_destroyed`, `.on_init`, `.on_built_tile`, etc. are
  **groups** that expand to several engine events.
- All registrations are collected and applied by a single **`Muluna.events.finalize_events()`**
  call at the end of `control.lua`. If you add a new `require(...)` of a control module that
  registers events, make sure it is required **before** `finalize_events()`, and never call
  `finalize_events()` twice.
- `on_init` group handler is also wired to `on_configuration_changed`, so keep it idempotent.
- GUI handlers are registered through `_G.gui_events` keyed by element-name pattern (see `lib/events.lua`).
- `Muluna.events.execute_later` / `register_delayed_function` schedule deferred calls using a
  hidden render object as a timer sentinel.

State lives in the `storage` table. Initialize it defensively in the `on_init` handler in
`control.lua` (guard with `if not storage.x then`). Never store references to `LuaEntity`
across ticks without re-validating `entity.valid`.

## Prototype authoring conventions

- New prototypes are added from `prototypes/*/index.lua` require chains rooted at `data.lua`.
  Add a `require(...)` to the relevant index/entry file rather than relying on autoload.
- Use `Muluna:extend{...}` (see above), not raw `data:extend`.
- **Patching existing prototypes** (vanilla or other mods) is done in `data-updates.lua`,
  `data-final-fixes.lua`, `prototypes/overrides/`, or `prototypes/final-fixes/`. Never assume a
  prototype exists — guard with `if data.raw.<type>["<name>"] then` (or `rro.safe_find`) because
  other mods may remove or rename things.
- Prefer `rro.soft_insert` / `rro.replace_no_duplicates` over `table.insert` when touching
  shared lists to avoid duplicate ingredients/effects/prerequisites.
- Deferred/last-resort patches belong in `prototypes/final-fixes/` and are required from both
  `data-updates.lua` and `data-final-fixes.lua` when they need to run at both times.
- Ground diggers are provided by PlanetsLib: `PlanetsLib.enable_ground_diggers()` in
  `prototypes/entity/ground-digger.lua` generates the shared `<drill>-ground-digger`
  prototypes, and `prototypes/final-fixes/ground-digger.lua` only adds Muluna-specific data.
- Localised names/descriptions use Factorio's LocalisedString tables, e.g.
  `localised_name = {"technology-name.rocket-part-productivity-muluna"}`.

## Compatibility patches (`compat/`)

- One file per mod, named after the mod. Each starts with a guard:
  `if mods["some-mod"] then ... end` or `if data.raw.planet["some-planet"] then ... end`.
- Loaded from `data.lua` (early) or `data-final-fixes.lua` (late) explicitly — there is no auto-discovery.
- Cross-mod behavior is often driven by `info.json` dependency entries. The operators matter:
  `"?"` optional, `"!"` incompatible/hidden, `"+"` at-least, `"(?)"` optional-but-hidden.
  Verify a mod's actual name before adding a dependency.
- `PlanetsLib.restrict_surface_conditions`, `APS.add_planet`, `APS.add_choice`, and
  `SP_BLACKLIST` (solar-productivity) are examples of hooking into dependency APIs.

## Migrations (`migrations/`)

- Files are named with a leading version and applied in order on save load.
- `.lua` migrations hold imperative code; `.json` files are declarative prototype patches.
- Use migrations when a change must be applied to **existing saves** (e.g. renaming/removing
  technologies, resources, or entities). New content does not need a migration.
- Renaming or deleting a technology requires updating all prerequisites that reference it —
  see the `delete_tech` helper in `data-final-fixes.lua` for the intended pattern.

## Bilingual/embedded content

`wood-gasification/` is a bundled mod-like feature with its own `settings.lua` and
`data.lua`, required from `settings.lua` and `data.lua` respectively. Treat it as
part of this mod while keeping its separate structure.

## Localization

- Translations live in `locale/<lang>/*.cfg`. English is the authoritative, complete locale.
- Do not machine-translate: the PR template explicitly requires reviewer knowledge of the language.
- When adding a new entity/item/tech, add the English keys (typically split across
  `locale/en/locale.cfg`, `item-name.cfg`, `greenhouse.cfg`).
- Changes to concepts shared with dependencies may belong in `PlanetsLib` / `Rigor Module` instead.

## Verifying changes

There is no CI test suite. What you can do:

1. **Static sanity**: re-read your Lua for stage mistakes (using `data.raw` in control,
   calling `data:extend` after `finalize_events`, etc.). There is no luacheck/stylua config
   in this repo, but `.vscode/` configures the `sumneko.lua` language server (disable
   `lowercase-global`; globals list includes `game`, `data`, `script`, `storage`, `mods`, ...).
2. **Loading the game**: the real check. Load a save with the mod enabled and confirm no
   startup crash. The PR checklist requires testing at least alone and with **Alien Biomes**.
3. **`funit` scenario**: `scenarios/__funit__can_generate_surface/` is a Factorio
   `__funit__` test that generates the Muluna surface and checks the Entity Replacement
   System. It needs the `funit` mod and a matching `mod-list.json`; it is a reference smoke
   test, not a general test runner.
4. **Crash reports**: because this mod deep-modifies Space Age, most bugs are load-time or
   interaction crashes ("Fixed crash on load with ..." is the most common commit type).

Because of the above, be conservative: guard prototype access, avoid assumptions about load
order, and prefer the `rro` helpers over raw table surgery.

## Commits, changelog, and releases

Releases and `changelog.txt` are **generated by `semantic-release` from commit messages** on
`main` (see `.releaserc` and `.github/workflows/release.yml`). The commit message *is* the
changelog entry, so it must follow **Conventional Commits** with the project's custom types.

Format: `type: Summary sentence.` (optionally `type(scope): ...`). Examples from history:

```
fix: Fixed crash on load with AAI Containers & Warehouses.
compat: Raised required PlanetsLib version to 2.0.8 ...
balance: Removed minimum temperature changes from vanilla generator prototypes.
feat: Added Space Boiler. ...
locale: Added Chinese localisation.
perf: ...
graphics: ...
other: Removed some now-obsolete console warnings.
```

`feat`/`feature` → minor bump; breaking → major; everything else (fix, balance, compat,
graphics, locale, sound, gui, perf, control, other, info, translate) → patch. The heading in
`changelog.txt` is derived from the type (e.g. `fix` → *Bugfixes*, `compat` → *Compatibility*).
Do **not** edit `changelog.txt` or bump `info.json` by hand for a normal change — CI does both.

Do not push to `main` without intent to release, and note the opencode `build` agent config
denies `git push`. The `Release` workflow publishes to the mod portal using `FACTORIO_TOKEN`.

## Documentation

`docs/` is LDoc output generated from source comments (config in `config.ld`, templates in
`docs_templates/`). Library modules document public functions with `---@param`/`---@return`
LuaDoc annotations and `-- @module` headers. Add doc comments to new `lib/` modules to keep
them in the generated API docs; do not hand-edit files under `docs/`.

## Working agreements

- Keep changes consistent with surrounding style: `local rro = Muluna.rro` at the top of files
  that patch prototypes, `Muluna:extend` for new prototypes, guarded `if mods[...]` for compat.
- Don't remove or "clean up" code you don't understand — a lot of it exists to dodge specific
  cross-mod conflicts, and there is heavy intentional use of commented-out code and workarounds.
- Prefer editing existing index/entry files to add requires rather than creating new auto-loaded
  conventions (there are none).
- `.env`, `*.zip`, and the built `docs/` are gitignored/untracked; never commit build artifacts
  or secrets.
